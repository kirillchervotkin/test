# Календарь турниров

`ScheduleModule` подключён в `AppModule`. Код разделён на контроллеры, DTO,
интерфейсы, сервисы, репозиторий, схему и маппер по образцу `test-grades`.
Существующие токены турниров и матчей сохранены. Их прежние реализации в памяти
заменены общим YDB-репозиторием. `assignments` и `rating` переведены на асинхронное
чтение матчей/назначений.

## Подготовка БД

DDL: `migrations/schedule/001-create-schedule.sql`. Это миграция **новой установки**:
шесть таблиц без внешних ключей и без удаления данных. Миграция не исполняется при
старте приложения. Перед применением проверьте существующие таблицы и сделайте
резервную копию; если имена заняты, требуется отдельная миграция существующих данных.
Исполните CREATE TABLE по отдельности средствами YDB, затем запустите приложение.
В DDL nullable-поля объявлены обычным типом, обязательные — `NOT NULL`.

Генерация, разворачивание шаблона, назначение команды и резолвинг выполняются в
serializableReadWrite-транзакциях. Чтение календаря — согласованный snapshot.
Параметры запросов типизированы; имена колонок берутся только из схемы.
JSON не используется как условие сравнения: настройки читаются и проверяются в TS.
Дерево этапов и агрегированный календарь собираются в сервисах после чтения YDB,
без предположения о поддержке рекурсивного CTE конкретной версией YQL.

## API

Все ID календаря в JSON — **десятичные строки Uint64**, например `"123"`,
а не JavaScript number. Это изменение контракта прежних in-memory DTO.
Даты турнира — `YYYY-MM-DD`, даты матчей — ISO 8601.
Swagger описывает маршруты, DTO и ошибки на русском.
Все маршруты schedule требуют JWT, кроме `GET /tournaments/:id/calendar`.

- `/tournaments`: POST, GET с season/type/dateFrom/dateTo; `/:id`: GET, PUT, DELETE.
- `POST /tournaments/from-template`: templateId, season, startDate, endDate.
- `POST /tournaments/:id/generate-schedule`: cityId, firstMatchDate?, intervalDays?.
- `GET /tournaments/:id/calendar`: tournament, stages, slots, matches, bracketSlots.
- `/tournaments/:tournamentId/stages`: POST, GET; `/tree`: GET.
- `/stages/:id`: GET, PUT, DELETE.
- `/tournaments/:tournamentId/team-slots`: POST, GET.
- `/team-slots/:id`: PUT с teamId, DELETE.
- `/tournaments/:tournamentId/matches`: POST, GET; `/matches/:id`: GET, PUT, DELETE.
- `/bracket-slots`: POST; `/:id`: PUT с resolvedTeamId, DELETE.
- `GET /stages/:stageId/bracket-slots`, `POST /stages/:stageId/resolve` (тело `{}`).
- `GET /stages/:stageId/standings`.
- `/templates`: POST, GET; `/:id`: GET, PUT, DELETE.

Старые маршруты матчей через `groups` заменены на stages. Старый модуль groups
остаётся независимым; его данные автоматически в stages не переносятся.

## Использование

1. Создайте турнир с name, season, type, startDate, endDate.
2. Создайте иерархию stages. В родительском этапе нет собственных слотов/матчей;
   календарь генерируется для конечных этапов.
3. Создайте team-slots с stageId и slotName; teamId можно не заполнять до жеребьёвки.
4. Запустите generate-schedule с существующим cityId. Повторная генерация — 409.
5. Назначьте команды через PUT team-slots: все связанные матчи обновятся.
6. Внесите оба счёта через PUT matches; после завершения источников вызовите resolve
   целевого этапа. Повторный resolve сохраняет результат.

`ROUND_ROBIN`: 2–128 слотов, 1–8 кругов; алгоритм Бергера, пропуск bye для нечётного
числа участников, обратное поле в чётных кругах. Очки: pointsForWin/Draw/Loss.
Тай-брейки по порядку: headToHead (мини-таблица команд с равными очками),
goalDifference, goalsScored, wins. При полной ничьей места делятся (`tied: true`),
автоматическая квалификация неоднозначного места запрещена.

`SINGLE_ELIM` и `DOUBLE_ELIM`: посев, bye без фиктивных результатов, 1 или 2 матча
в серии. Для ссылки на серию sourceMatchId — ID последнего матча; учитывается сумма
обоих матчей. При равном счёте задайте `settings.decisions[ID_последнего_матча] = ID_победителя`
и повторите resolve. Правило выездного гола не применяется.
DOUBLE_ELIM имеет нижнюю сетку; grandFinalReset по умолчанию true. Запасная финальная
серия заранее присутствует в календаре, но команды в неё попадают только при
поражении победителя верхней сетки в первом финале.

Квалификация задаётся в settings.qualification: slotName, sourceType и источник
GROUP (sourceStageId/sourcePosition, при необходимости sourceGroupName) либо
WINNER/LOSER (sourceMatchId). Шаблоны вместо ID этапа используют sourceStageKey.
Групповые источники ждут завершения всех матчей. Циклы запрещены.
Финалы назначаются после последнего матча группы-источника.
Интервал по умолчанию 1 день; круговые матчи одного тура имеют одну дату, матчи
серий плей-офф идут последовательно. Планирование занятости судей/стадионов сюда
не входит. Все матчи используют переданный город; neutralVenue хранит регламент,
отдельный подбор площадок по нему не выполняется.

## Шаблон

Смотрите `examples/group-playoff.json`: тело POST /templates. После создания
передайте полученный templateId в POST /tournaments/from-template. Поле cityId
должно ссылаться на существующий город. Слоты в примере не требуют команд заранее.
settings.generated — внутренние метаданные серии и календаря; клиент задавать их
не может. Неизвестные настройки отклоняются, в частности exchange пока не имеет
реализованной семантики. Расширение регламента требует кода правил, но не новых таблиц.

## Ограничения интеграции

- Миграция применена к YDB из локального `.env` 19.09.2026: проверены типы,
  nullable-поля, первичные ключи всех шести таблиц и SELECT через ScheduleRepository.
  Запись бизнес-данных этим запуском не проверялась. Автотесты используют
  транзакционный тестовый store; HTTP-тест подменяет guard и справочники.
- Города и команды сохраняются в YDB; API справочников сохраняет числовые safe-integer ID.
  Миграция и проверка перезапуска описаны в `migrations/references/README.md`.
  Существующий модуль assignments пока остаётся in-memory.
- Удаление турнира с матчами, отдельного сгенерированного матча, используемого этапа
  и изменение уже использованных результатов запрещены с 409. Это консервативная
  политика; откат завершённой сетки и удаление всего календаря не реализованы.
- Ручное назначение работает для незаполненного слота; замена уже прошедшей дальше
  команды требует отдельной операции отката, поэтому сейчас возвращает 409.
- Генерация выполняется одной транзакцией: очень крупные шаблоны могут превысить
  лимиты YDB. Для них нужен отдельный пакетный механизм публикации календаря.

## Проверки

```sh
npm run build
npx vitest run src/schedule/schedule.spec.ts
node test/schedule-http.mjs
node test/schedule-repository.mjs
```

Тестируются чётные/нечётные круговые сетки, одинарное/двойное выбывание, bye,
двухматчевые серии, reset финала, ничьи, атомарный откат генерации, иерархия,
квалификация, HTTP-валидация, публичный календарь и Swagger.
Новые файлы совместимы со strict TypeScript; полное включение strict для всего
старого проекта выявляет ошибки его существующих DTO и не выполнено автоматически.
